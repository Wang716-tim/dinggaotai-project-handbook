O02在原2人日预算内拆成两个检查点：O02-PRE准备预发布回滚/首次停入口演练、四方证据包；O02-RELEASE执行正式发布。PRE依赖Q02/O01及候选产物，RELEASE额外依赖PRE通过、公开前置证据齐备及用户发布确认。准备/内部演练不依赖公开手续完成，不形成“先上线才能演练”的循环；若2人日实测不足，走缓冲或重新估算，不假装已完成。

外部前置登记于部署手册，每项必须有责任人、实际状态、证据位置及阻塞目标。公开事项缺失只阻塞RELEASE；收款资格与凭证流程额外阻塞真实收费。产品经理在D01跟踪，外部办理人力/费用若超出现有范围须单独提交，不计作已获预算。

## 避免依赖死锁

B02 先基于附件 READY 契约实现项目与版本；B03 独立完成附件状态；B06 的任务领取协议在 T01 定义，文件任务在 B03 开发时即实现所需基础部分，B06 再完成通知消费。这里的任务编号不是必须串行完成的顺序。

同一位后端开发按“身份 → 任务基础 → 文件 → 发布 → 审阅 → 决定 → 通知和清理”顺序实施。前端可用与契约一致的模拟响应推进，模拟通过不能代替真实联调。

v1.3 [首批任务卡](../11_开发启动包/04_首批任务卡.md)把原任务内部的消费边界展开：B04-GRANT先交付可加入发布事务的授权原语，B02-PUBLISH消费它；完整B04客户入口仍在发布之后联调。这是原B04范围内拆分，不增加端点或原118人日。首批分项77人日、B06后续2人日及其余原任务39人日仍合计118。

## 每张任务卡的完成标准

有需求和用例映射；遵守数据与 API 基线；成功与失败路径都有证据；没有暴露凭据或跨空间数据；必要文档已更新；评审者确认；遗留项有责任人和截止时间。因外部手续未完成的发布任务保持阻塞，不虚标完成。
