# 任务卡模板

使用方法：复制到后续任务记录区，一张卡只承载一个主模块交付。以下空项必须在执行前填完；这不是一个已领取任务。

| 字段 | 填写要求 |
|---|---|
| 任务ID／标题 | 引用任务拆解编号，说明可观察结果 |
| 需求／假设ID | R编号或H编号，不能只写“优化体验” |
| 主模块／负责人／验收人 | 一名直接负责人及独立验收角色 |
| 当前状态 | READY/IN_PROGRESS/REVIEW/TESTING/BLOCKED/DONE |
| 目标与用户价值 | 完成后用户能做什么 |
| 必读上下文 | 项目速览、全局约束、本模块、必要契约章节链接 |
| 输入与前置 | 身份、对象状态、上游接口和已通过的门槛 |
| 允许修改范围 | 文档或未来代码目录，以及契约版本 |
| 不在范围内 | 明确相邻模块和P1内容 |
| 交付物 | 功能/文档/测试证据/迁移说明 |
| 验收 | 给定条件、操作、预期结果；至少一个失败路径 |
| 人日与依赖 | 预算、前置任务、最晚交付时间 |
| 模型／思考／执行上下文 | 推荐参数、实际请求参数、代理ID及必要输入；不要把人工人日当AI运行时间 |
| 风险与阻塞 | 已知不确定性、需要谁解决 |
| 完成证据 | 实际构建、环境、测试链接和日期 |

## 示例：B05中的并发决定子任务

目标：同一版本同时提交两个最终决定时，只有一个成功且记录正确。允许修改M05事务和相关集成测试；不得修改客户登录或增加会签。前置为已发布版本、有效客户会话和冻结的API契约。验收为两个并发请求，一个成功，另一个返回已决定；数据库仅一条Decision与Receipt，版本终态匹配成功请求；邮件失败不改变该结果。

示例是未来任务定义，没有实施或测试结果。
