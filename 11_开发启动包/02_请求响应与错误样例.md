# 请求响应与错误样例

v1.3 开发准备。路径均位于 `/api/v1`，字段以[公共 API 契约](../02_开发手册/02_API契约.md)为准。表中 `P`、`V1` 等是[固定 UUID](03_合成数据与页面接口映射.md#实体键)的引用，线路上使用完整字符串。尖括号内是合成凭据、文件流或待生成的摘要。内部和客户会话隔离，写请求含对应 CSRF 与 Origin 校验。

成功响应有 `data` 和本次调用的 `request_id`，分页另含 `next_cursor`，末页为 `null`。失败响应有 `error.code`、`error.message`、可选的 `error.fields` 和本次调用的 `request_id`。204 无响应体。以下是创建项目后的线路示例。

```json
{
  "data": {
    "id": "045cc99f-7e4a-488d-a9c9-f900ac067ce8",
    "title": "夏季活动海报",
    "status": "ACTIVE",
    "current_version_id": null,
    "revision": 1
  },
  "request_id": "02784354-5638-4df6-9bea-ef84ce82d49a"
}
```

## 核心对象

| 返回对象 | 字段与本例取值 |
|---|---|
| `Project` | `id`、`title`、`status`、`current_version_id`、`revision`。P 的当前发布指针依次为 `null`、V1、V2，创建 V2 草稿时仍指向 V1。 |
| `Version` | `id`、`project_id`、`number`、`status`、`title`、`description`、`assets`、`revision`、`published_at`。V1/V2 的标题分别为“夏季活动海报 v1”“夏季活动海报 v2”，说明为“海报与印刷说明初稿”“活动日期更新至 7 月 19 日”。新建为 `DRAFT`、`assets=[]`、`published_at=null`。发布时刻见[时间线](03_合成数据与页面接口映射.md#合成时间线)。 |
| `Asset` | `id`、`display_name`、`kind`、`bytes`、`status`、`failure_code`。类型为 `JPEG`、`PNG`、`PDF`，本例海报为 `JPEG`。成功处理时 `failure_code=null`。 |
| `Comment` | `id`、`version_id`、`asset_id`（可为 `null`）、`author_kind`（`MEMBER` 或 `GUEST`）、`body`、`created_at`。列表和新增共用此形状。M1 属于 V1/A11、`GUEST`，正文“海报标题里的活动日期有误。”，时间为 `2030-03-18T01:13:00Z`。作者私密 ID 不下发。 |
| `Decision` | `id`、`version_id`、`outcome`、`message`、`decided_at`、`receipt_id`。D1 对应 V1/R1，结果 `CHANGES_REQUESTED`，说明“请把海报标题日期从 7 月 12 日改到 7 月 19 日。”，时间 `2030-03-18T01:16:00Z`。D2 对应 V2/R2，结果 `APPROVED`，备注“确认此版用于活动制作。”，时间 `2030-03-18T01:38:00Z`。 |

revision 使用提交前服务端读取值。下例为两次发布各取项目 revision 2、4，版本 revision 7。发布后版本 revision 为 8，决定后为 9。这些数值用于回放样例，版本变动和评论是否影响 revision 以[状态机](../01_项目手册/05_业务流程与状态机.md)为准。

## 第一轮 · 客户要求修改

| 步骤 | 请求样例 | 预期响应及检查 |
|---|---|---|
| 1 · `POST /projects` | `title="夏季活动海报"`，幂等键 `fixture-project-01` | `201`，`data=Project`，P 为 `ACTIVE`。 |
| 2 · `POST /projects/{P}/versions` | `title="夏季活动海报 v1"`，`description="海报与印刷说明初稿"`，键 `fixture-draft-01` | `201`，`data=Version`，V1 为第 1 轮 `DRAFT`，revision 为 1。 |
| 3 · 两次 `POST /versions/{V1}/uploads` | `{display_name:"活动海报.jpg",declared_bytes:1048576,kind:"JPEG"}`，键 `fixture-upload-11`。`{display_name:"印刷说明.pdf",declared_bytes:524288,kind:"PDF"}`，键 `fixture-upload-12` | 两次 `201`，`data={upload_id,asset_id,expires_at}`。分别得到 U11/A11 与 U12/A12，接收期限见[时间线](03_合成数据与页面接口映射.md#合成时间线)。 |
| 4 · 两次 `PUT /uploads/{id}/content` | 对 U11 传 JPEG（`Content-Type: image/jpeg`），对 U12 传 PDF（`Content-Type: application/pdf`）。二进制流声明各自长度。 | `202`，`data=Asset`，状态 `PENDING_SCAN`。每份已完整接收的内容只能写入一次。 |
| 5 · `GET /uploads/{id}`、`GET /assets/{id}` | 使用相应预留 ID、附件 ID | `200`，预留返回 `data={state:"PROCESSING",asset_id:A11,received_complete:true,expires_at:"2030-03-18T01:17:00Z"}`，完成处理后可为 `SETTLED`。附件最终为 `READY`。`expires_at` 只约束接收窗口。 |
| 6 · `POST /versions/{V1}/publish` | `{reviewer_email:"client@example.test",expires_in_days:7,expected_project_revision:2,expected_version_revision:7}`，键 `fixture-publish-01` | `201`，`data={version,share_id:S1,share_url:〈合成链接〉}`，version 为 `IN_REVIEW`，P 指向 V1。至少一份且全部 `READY`，已发布内容冻结。 |
| 7 · `POST /review/challenges` → `POST /review/verify` | 挑战传 S1 对应的合成 `share_token`、`email="client@example.test"`。验证传同一个 `share_token`、`challenge_id=C1`、`code="481205"`。 | 挑战 `202`，统一提示及 C1，只有资格有效且邮箱匹配才发码。验证 `200` 设置客户会话 Cookie，`data={version}`，其中 version 为 V1。 |
| 8 · `GET /review/version`、`GET /review/comments`、两个附件的 `POST /review/assets/{id}/download` | 客户只读当前授权轮。A11 传 `variant="preview"`（也可请求 original），A12 传 `variant="original"` | `200`，业务数据分别为 `data={version,decision:null}`、`data=[]` 的分页响应、`data={url,expires_at}` 的签发响应。图片预览为重编码版本，PDF 仅下载，URL 有效 60 秒。 |
| 9 · `POST /review/comments` | `{version_id:V1,asset_id:A11,body:"海报标题里的活动日期有误。"}`，键 `fixture-comment-01` | `201`，`data=Comment`，M1 属于 V1/A11，客户及内部页面按纯文本呈现。内部公开回复用 `POST /versions/{V1}/comments`，由路径绑定版本，提交 `asset_id`（可为 `null`）和 `body`，用独立幂等键。返回 `MEMBER` 评论。主线只提交 M1。 |
| 10 · `POST /review/decisions` | `{version_id:V1,outcome:"CHANGES_REQUESTED",message:"请把海报标题日期从 7 月 12 日改到 7 月 19 日。",acknowledged:false,acknowledgement_version:null,expected_version_revision:8}`，键 `fixture-decision-01` | `201`，`data=Decision`，D1 引用 R1。V1 进入 `CHANGES_REQUESTED`，有效授权下仍可读本轮和固定记录。后续评论拒绝。 |

## 第二轮 · 客户确认完整新版本

| 步骤 | 请求样例 | 预期响应及检查 |
|---|---|---|
| 11 · `POST /projects/{P}/versions` | `title="夏季活动海报 v2"`，`description="活动日期更新至 7 月 19 日"`，键 `fixture-draft-02` | `201`，V2 为第 2 轮 `DRAFT`，P 仍指向 V1。 |
| 12 · 重走上传步骤 3—5 | JPEG 文件“活动海报.jpg”，`declared_bytes=1179648`，键 `fixture-upload-21`。PDF 文件“印刷说明.pdf”，`declared_bytes=589824`，键 `fixture-upload-22`。 | 用 U21/A21、U22/A22 接收两份新原件，接收期限分别为 `2030-03-18T01:38:00Z`、`2030-03-18T01:38:20Z`。本例两份都在 01:30Z 发布前完成接收和扫描，成为 `READY`。 |
| 13 · `POST /versions/{V2}/publish` | `{reviewer_email:"client@example.test",expires_in_days:7,expected_project_revision:4,expected_version_revision:7}`，键 `fixture-publish-02` | `201`，事务提交 V2、S2、当前指针及旧授权撤销，首响附一次性链接。S1/G1 失效，V1 保留 D1/R1。若旧轮仍审阅中，旧状态改为 `WITHDRAWN`。 |
| 14 · 重走客户步骤 7—8 | 用 S2 对应的合成密钥、C2 和 `code="642819"` 验证，取得新会话 G2。 | `GET /review/version` 返回 V2、A21/A22 和 `decision:null`，本轮评论为空。 |
| 15 · `POST /review/decisions` | 确认框展示 v2、发布时间、两份完整文件名和文件数。客户勾选说明后，以键 `fixture-decision-02` 提交下例。 | `201`，`data=Decision`，D2 引用 R2。V2 为 `APPROVED`，即使随后邮件发送失败也保持已提交的决定。 |
| 16 · `GET /review/receipt`、两个版本的 `GET /versions/{id}/receipt`、`GET /versions/{V2}/receipt/export` | G2 读取 R2，内部会话可按版本分别读取 R1、R2。 | JSON 读取 `200`，`data=Receipt`。下载文件本体是同一 Receipt 对象，打印取相同快照。之后修改项目名，历史记录继续显示决定时名称。 |

```json
{
  "version_id": "a3e318c0-012d-4ead-b502-ace7a6d4c740",
  "outcome": "APPROVED",
  "message": "确认此版用于活动制作。",
  "acknowledged": true,
  "acknowledgement_version": "REVIEW_CONFIRM_V1",
  "expected_version_revision": 8
}
```

两种请求都带布尔 `acknowledged` 与 `acknowledgement_version`。要求修改需 1—2,000 字符说明，传 `false` 和 `null`。确认传 `true` 和 `REVIEW_CONFIRM_V1`，备注可为空，最多 2,000 字符。缺勾选、字段类型或文案版本不符时拒绝提交。本例确认说明为“我确认本次列出的交付文件。提交后本轮决定封存，更正需联系工作室新开一轮。”

## 固定记录响应

R2 的结构与字段如下。R1 使用同一形状，填入 V1/A11/A12、M1、D1、G1 的验证时刻，以及 `acknowledgement_version=null`。结构中的 SHA-256 和快照摘要留出占位，合成样例未生成实际文件或快照。正式模式、摘要算法和编码在 T01 冻结。

| 字段 | R2 示例 |
|---|---|
| `id`、`decision_id`、`schema_version` | R2、D2、`1`。 |
| `outcome`、`message` | `APPROVED`、“确认此版用于活动制作。” |
| `project_snapshot` | `{id:P,title:"夏季活动海报",workspace_name:"沿岸设计"}`。 |
| `version_snapshot` | `{id:V2,number:2,title:"夏季活动海报 v2",description:"活动日期更新至 7 月 19 日",published_at:"2030-03-18T01:30:00Z"}`。 |
| `files_snapshot` | `[{id:A21,display_name:"活动海报.jpg",position:1,bytes:1179648,mime:"image/jpeg",sha256:〈A21 原件摘要〉},{id:A22,display_name:"印刷说明.pdf",position:2,bytes:589824,mime:"application/pdf",sha256:〈A22 原件摘要〉}]`。 |
| `comments_snapshot` | `[]`。R1 中为含 M1 的 Comment 数组。 |
| `identity_method` | `{verified_email:"client@example.test",verified_at:"2030-03-18T01:34:00Z",decided_at:"2030-03-18T01:38:00Z",description:"本记录用于记录本轮交付反馈与确认；邮箱验证表示当时能够接收该邮箱验证码，不代表实名、企业授权核验或电子签章。",acknowledgement_version:"REVIEW_CONFIRM_V1"}`。 |
| `snapshot_digest` | 〈R2 快照摘要，编码与算法由 T01 冻结〉。 |

## 超时、冲突与权限

各分支独立从相应状态开始，已冻结的状态码沿用公共契约。校验等仍有 HTTP 选择的条目用于展示页面行为。

| 触发 | 预期及恢复 |
|---|---|
| 决定 POST 响应丢失或返回 503 | 保留原 `version_id`、请求内容和幂等键，显示“正在核实提交结果”。先 `GET /review/version`，核实仍授权同一轮。如果有决定，`GET /review/receipt`，按服务端记录显示。若仍不确定，且授权有效、原请求可复用，使用原键和原请求重试原 POST。授权失效/切换时结束该提交入口并显示对应状态，严禁更换键自动提交。 |
| 24 小时记录有效期内同键同内容重放，权限复核通过 | `200`，返回原业务结果。决定仍是原 D2/R2，虽当前 revision 已为 9，重放仍使用原请求内 revision 8。没有新增决定、记录或通知。 |
| 决定已存在，用新键再提交同轮有效请求 | `409 ALREADY_DECIDED`，从 `GET /review/version` 及 `GET /review/receipt` 取得既有结果。 |
| 同身份同路由同键但改了 `message`，或同键等待首事务超时 | 改内容 `409 IDEMPOTENCY_CONFLICT`。等待超时 `503 SERVICE_UNAVAILABLE`，保留原键原内容，从业务读端点核实或按原请求重试。 |
| 发布或重发成功请求重放 | `200`。发布 `data={version,share_id,secret_replay_available:false}`，重发 `data={share_id,secret_replay_available:false}`。原链接只在首响给出。需要新链接时，用户显式调用 `POST /versions/{V2}/shares`，传 `expires_in_days=7` 和新键，例如 `fixture-reshare-02`。`201`，`data={share_id:S2R,share_url:〈替换链接〉}`，沿用原邮箱，撤销 S2/G2。撤销某分享用 `DELETE /shares/{id}`，`204`，保留版本状态。 |
| 发布用旧 revision，或草稿已存在 | `409 REVISION_CONFLICT` 刷新项目和版本，用户重新检查清单及邮箱。禁止静默带新 revision 提交。`409 DRAFT_EXISTS` 引导打开现有草稿。 |
| 上传响应丢失 | 先用 `GET /uploads/{id}` 核对 `received_complete` 与 `state`。完整接收的原件只轮询或读取附件处理结果。未完整接收，等待释放旧预留后，用新键申请并上传。不可覆盖已完整接收的内容。 |
| 发版时无文件或有 `PENDING_SCAN` 附件 | `409 STATE_CONFLICT` 示例。指出未就绪原因，等所有附件 `READY` 后由用户重新确认。发布失败无有效新分享或指针变化。 |
| 文件超限、非法或处理失败 | `declared_bytes=26214401` 使用 `413 FILE_TOO_LARGE`，指出上限 25 MiB。非法类型使用 `UNSUPPORTED_FILE`。完整原件的可重试 `FAILED` 用 `POST /assets/{id}/retry`（`202`）。`REJECTED` 或原件不完整时重新选文件。存储额度不足用 `429 QUOTA_EXCEEDED` 示例，显示占用原因。 |
| 新会话授权 V2，旧页提交 V1 评论或决定、下载 A11 | 旧版操作拒绝，刷新授权轮并引导回正确链接。撤销链接使用 `410 SHARE_UNAVAILABLE`，会话过期使用 `401 SESSION_EXPIRED`。重叠条件的错误顺序在 T01 冻结。 |
| W2 会话读取 P 或 A11，或内部会话代客户决定 | 跨租户读取 `404 RESOURCE_NOT_FOUND`，对外与不存在一致。内部身份无决定权限。客户 Cookie 也不能访问内部历史。 |
| 只读空间中客户提交决定、Editor 重试失败附件 | `403 WORKSPACE_READ_ONLY`。有效既有授权仍可验证、读取和下载，保护性操作按权限表。缺少有效 CSRF 或 Origin 不符时拒绝，如 `403 CSRF_FAILED`。 |
| 输入 `other@example.test`、验证码过期或限流 | 挑战仍用统一提示，邮箱不匹配时无发件。过期后按规则重发，新码使旧码失效。`429 RATE_LIMITED` 显示可行动的等待提示，保留原输入。 |

HTTP 409 的失败包络示例。当前有效授权下，已有决定，客户端使用了新键再次提交。

```json
{
  "error": {
    "code": "ALREADY_DECIDED",
    "message": "本轮已有决定，请查看本轮结果。"
  },
  "request_id": "0139aaf1-d31c-4b50-9849-d201719b7903"
}
```

## 待定设计

T01 联合冻结正式请求及响应模式、字段可选性、错误细分与测试夹具。可先使用本页已明确的核心字段和合成分支评审，不据此生成生产客户端。

| 项 | T01 待冻结内容 |
|---|---|
| 身份与会话 | 挑战统一提示字段、内部验证与 `/me` 各身份摘要、CSRF 引导、Cookie 及会话更新测试。 |
| 边界格式 | 接收长度头、`error.fields` 的内容、`retry_after` 位置，以及权限、过期、revision 和状态重叠时的错误顺序。 |
| 固定记录 | 快照版本字段的兼容规则，快照摘要算法、规范化序列化与编码；附件原件已确定使用SHA-256，T01补实际文件样本复算证据。内外记录、导出和打印使用上面同一业务结构。 |
| 受控运营操作 | 按[受控运营操作规格](../02_开发手册/08_受控运营操作规格.md)冻结首次Owner核验、后台入口、字段模式、权限配置及审计实现，执行A20-a/A21/A31等实际分支；不新增自助建空间或其他公开API。 |
