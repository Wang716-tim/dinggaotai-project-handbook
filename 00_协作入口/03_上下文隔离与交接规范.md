# 上下文隔离与交接规范

## 原则

模块分工用于减少无关上下文和重复决策，不隔绝必要的业务依赖。每个结论必须能回到一份权威文档。聊天中的临时建议没有自动覆盖文档的效力。

## 领取任务

1. 项目经理填写 [任务卡](../05_协作模板/01_任务卡.md)，明确需求 ID、模块、契约版本、验收场景及禁止修改范围。
2. 成员先读最小上下文，再读本模块引用的具体契约章节。
3. 用自己的话写出目标、输入输出和三个关键不变量；不一致时先查权威文档。
4. 只处理任务卡中的交付物；发现跨模块问题，提出带影响范围的变更请求。

## 文档权威表

| 事项 | 唯一权威位置 | 批准角色 |
|---|---|---|
| 首版范围／验收 | 产品需求与验收 | 产品负责人 |
| 全局数值限制 | 术语与全局约束 | 产品 + 技术负责人 |
| 状态变化 | 业务流程与状态机 | 产品 + 后端负责人 |
| 字段、唯一性、索引 | 数据模型 | 技术负责人 |
| 请求、响应、错误、幂等 | API 契约 | 前后端负责人共同确认 |
| 发布／恢复条件 | 部署与发布手册、备份与事故处理 | 发布负责人 |

模块包只能补充实现责任，不能另立同名状态、权限、限制或接口。引用发现冲突时登记 C 编号，按上表修正文档，并通知受影响角色。

## 人与 AI 协作的任务上下文

输入包固定为：任务卡 + 项目速览 + 全局约束 + 本模块包 + 必要契约节选 + 最近一份交接单。目标上限约 6,000 中文字；复杂任务允许扩展，但说明新增材料用途。不要把完整聊天、其他模块推测方案、生产日志或客户原始文件作为默认输入。

向 AI 提供的任务文本应明确：“当前仅允许处理任务卡范围；未知事实标记待确认；不要以推测变更公共契约；返回变更清单、验证证据和未解决项。”这是一项协作规范，不代表已经启动任何代理或编码。

## 冲突和变更

提交变更前列出：原因、受影响需求、字段/API/状态变化、兼容性、迁移影响、增加的人日和验证方法。技术负责人评估接口；产品负责人决定范围；项目经理调整依赖。批准后先更新权威文档，再同步消费者，最后开始实现。

文档版本采用 v主版本.次版本：语义不兼容提升主版本，兼容补充提升次版本，排版修正记录日期即可。API 使用 /api/v1 路径；不兼容变更不能偷偷保留旧版本名。

## 完成与交接

交接单必须列出实际完成、尚未完成、契约版本、测试与证据位置、剩余风险、下一步入口。写明“待验证”比空泛写“已完成”更有价值。下一位成员应能仅凭交接单找到必要材料，不用翻阅全部聊天。

任何同一文件的并行编辑都需明确负责人；合并由负责人完成。多人可并行阅读和独立模块工作，不同时改写公共契约。每周一次检查死链接、重复定义、变更未传播和无主任务。
