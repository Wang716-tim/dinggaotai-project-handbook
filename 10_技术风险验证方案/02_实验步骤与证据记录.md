# 实验步骤与证据记录

2026-11-20，v1.3 验证准备。以下步骤供阶段获准后执行。所有实际结果栏当前为未执行。判定与责任见[实验清单与放行门槛](01_实验清单与放行门槛.md)。

## 公共执行约定

- 只用隔离环境、合成文件、合成账号和空间。存储测试使用独立私有测试桶或具备等效隔离的测试边界，先确认环境、清理身份、允许的前缀、费用边界和出站目的地。数据库并发用真实 PostgreSQL。以固定时钟验证业务时间边界，涉及真实 OSS 在途写入和恢复耗时的分支使用实时时间。
- 预先登记每个分支的合成数据摘要、提交屏障、故障点、观测渠道和停止条件。时序故障优先用可确认到达的屏障，保存服务端提交顺序及外部事件时间。外部响应丢失和实际请求结束要分别打点。客户端在上传途中被杀能否重现存储已接受的分支，需要独立证据。
- 每个分支收集相同的关联标识和 UTC 时间。隔离保存诊断原件，仅在评审引用脱敏后的运行号、匿名标识、对象标识映射、摘要、请求号和时间线。测试报告里禁止保存验证码、签名 URL、Cookie、密钥或原件正文。
- 一发现越权、对象逃逸、重复业务副作用、账目失真或连接到非测试资源，停止故障注入并保留相关证据。关闭该测试入口和新写入，逐项核对测试资源归属、对象引用、待决写入和预算。未知写入隔离并保账，按协议继续取证。清理工件前保全最少必要证据。

## TR01 · 写入能力与执行隔离

**阶段与责任**　T01 技术负责人、运维。Q02 由测试与 B03 后端复验。对应 A05/A06/A19/A28 的写入前提。

**前置**　独立签发、执行和回收身份已在隔离配置中核对。记录存储接口与 SDK、各阶段的观测点、执行总上限和时钟误差，准备同尺寸不同摘要的合成图片。

1. 为合成图片准备原件及预览两种分支，记录其各自的登记请求序号、长度、摘要与唯一对象 key。分别暂停在写入台账事务提交前、提交后、能力发放后。事务回滚分支确认外部写入未启动。正常分支核对存储返回与实际长度及摘要。
2. 在隔离环境逐项验证错误方法、错误 key、错误长度、错误摘要、越权的列举/删除、已过期能力及试图越出测试前缀时的行为。使用带受控响应的实验代理确认重定向和传输错误不会引发额外发送。需要合法重试时，先证明旧请求终结、再登记新序号并重新确认代际、预算及单一待决写入。有效窗内的重放风险交 TR02 验证。
3. 一组让外部请求跨越输出写入硬截止，观察 60 秒截止触发停止发送与子进程终止。另一组在能力尚有效时使执行器续租失败，核对旧代不再启动请求、签发方拒绝旧代申请。确认能力有效期不超过 120 秒，也不超过签发时所剩租约。验证扫描子进程禁出站、存储执行子进程仅获本次能力，二者均无长期凭据。

**观测**　能力发放时间、台账提交时间、方法/key 映射、声明与实际字节、摘要、代际、能力到期、请求截止、外部发送次数及去向、执行器存活、存储响应和对象清单。

**判定**　两种合法写入均符合登记和权限边界，异常分支无越权对象、无发放前写入、无隐式发送，判为通过。任何约束可绕过或旧代能新发请求判失败。仅见 SDK 表面错误、无发送侧或存储侧可核验数据时为证据不足。

**停止与清理**　发现越权或非测试目标先封闭本次签发和出站。已签发窗口及未知操作交 TR02 核验，依协议清理本次台账对象。

## TR02 · 未知写入、终结取证与清理重放

**阶段与责任**　T01 技术负责人、运维在实际 OSS 测试环境验证存储路径和最小回收事务。Q02 用 B03/B06 候选回归。对应 A28。

**前置**　准备 TR01 同配置的原件及预览路径、可控制放行和丢响应的测试观测点、独立可登录的回收者、填满空间预算的旧代、可等候的新代及删除代际对照。T01 通过最小台账和事务验证，Q02 使用产品的入口、页面、任务和引用复验。冻结故障观察截止与测试可接受的最长阻塞观察期，记录这两项仅用于实验排程。

1. 使用独立回收角色、合成原件/预览、两代执行者和额度已满的测试数据。先跑能收到完整成功响应或存储明确拒绝的对照，记录存储端请求号及独立查询粒度。
2. 隔离完成每类时序。让请求已发送且客户端响应丢失，让 A 永久停在回收者不可依赖的状态。通过受控延迟观察一次 `HEAD` 暂空后写入才终结，再覆盖能力到期前迟发和已签发能力重放。若实验只能证明客户端或代理端的时序，标明实际存储接受时刻和终结时刻仍缺证据。补测 A 失租但稍后恢复，以及活动删除请求和接管竞争。复验时保留 Q02 的发布引用检查。
3. 回收者从台账独立定位能力有效窗、签发权限、发送/可能发送的范围和全部可能重放。记录所有已签发能力到期、旧代无法再获能力，以及所有已接受或可能接受的请求已终结的证据、覆盖条件和采集限制。分别验证暂时无法取得证据、证据随后齐备，以及持续无法取得证据的情形。能力未到期、采集延迟或存在覆盖空洞时，写入留在 `UNKNOWN`，原预算继续保留，额度不足的新代进入 `WAITING_CLEANUP`，普通失败计数保持原值。检查 `ATTEMPT_RECONCILE` 的每分钟扫描、十分钟进入 `BLOCKED_CLEANUP` 并告警，以及一小时内部响应目标的交接。核对页面提示“处理受阻，正在核查存储状态”。
4. 证据齐备后核对空间、项目、代际、台账及引用，注入一次删除拒绝或失败，再恢复权限。另在外部清理已确认而结算尚未提交时中断回收者，并发重放回收。核对只有一次 `CLEANED` 账目转换和合法候补获唤醒，删除中的项目只收尾，旧代不能建立发布引用。

每个分支重新准备初始对象、台账和额度。真实存储证据与故障注入器记录分别留存，供复核者判明哪些外部事件实际发生。

| 分支 | 注入或观测点 | 该分支需要的断言 |
|---|---|---|
| 成功和明确拒绝对照 | 控制端取得完整存储响应 | 请求号和终态可关联。能力窗尚开放时仍需核查可能重放 |
| 响应丢失及暂空 | 丢弃返回给执行者的响应，核实存储已接受。先观测 `HEAD` 暂空，再用正向证据确认迟到写入终结 | 任一次暂空时均保账，回收者在原执行者失联时独立定位并确认终结 |
| 迟发和重放 | 能力到期前发送已签发请求。独立分支在有效窗内重复使用同一能力，另测试到期后发起 | 迟发和重放的实际接受、拒绝及终态均可解释。已接受的请求跨越到期时仍由回收者举证。能力到期后发起的新请求不能成功写入 |
| 无法举证 | 已知路径存在待决请求，暂不可获取足以覆盖能力窗的证据 | 原代保账，新代无独立预算则等待，按时告警和升级。证据恢复后才允许清理。永久缺证据持续阻塞 |
| 旧代返回、删除并发 | 使旧代在失租后尝试回报结果，同时由当前代接管或发起删除 | 旧代不能创建发布引用或结算。有效删除完成时只收尾，取消删除的合法草稿从新代际及去重键继续 |
| 删除失败 | 在有终结证据后让回收者收到明确删除失败，再恢复清理权限 | 清理失败期间保账。权限恢复后核对所有已登记残留，再事务结算 |
| 回收者崩溃及重复领取 | 外部清理后、账目提交前中断，再引入两个尝试领取的回收者 | 只产生一次提交的 `CLEANED`、一次释放及一次合法候补唤醒 |

**观测**　`ObjectWriteAttempt` 的请求序号、key 映射、写入能力有效窗、截止时间、响应、`storage_request_id`、终结证据引用；处理代际、预算、队列与失败计数；存储端接受/终结/查询时间、查询覆盖和已知缺口；`HEAD` 与删除响应；结算前后字节数、告警及候补领取时刻。对窗口证据单独附数据源适用范围、完整性边界及独立复核记录。

**证据边界**　桶访问日志投递可能延迟，指定时间区间记录无完整性保证，且中断请求不在该日志中。可关联到具体请求的正向日志辅助核对终态，实时查询也须单独证明覆盖中断、迟发、无请求号及可能重放的请求。日志空白、单条请求号、瞬时 `HEAD` 暂空、客户端超时或运维确认收到告警均不能证明窗口终结。日志时间范围须考虑相邻时间段、查询延迟与时钟误差，发布的证据只引用脱敏记录。参见[OSS 桶访问日志官方说明](https://www.alibabacloud.com/help/en/oss/user-guide/logging)、[OSS 实时日志查询官方说明](https://www.alibabacloud.com/help/en/sls/usage-notes-of-oss-access-log/)。

**判定**　所有故障分支满足未知保账、无旧代引用、证据齐备后清理及唯一结算，且能由独立回收者在真实 OSS 上证明未知写入终结，T01 才通过。提前释放、无证明删除、重放多结算或未告警判失败。若能复现安全阻塞而真实环境始终无终结证明、无法触发迟到写入或观察不到覆盖范围，TR02 整体证据不足，B03 写入路径不放行。

**停止与清理**　到达预登记观察时限仍无证据时，结束注入并保留隔离台账与预算，记录阻塞及升级责任。独立回收者取得完整证据后按授权清理，再核对测试资源及账目。

## TR03 · 额度接续、并发预留与只结算一次

**阶段与责任**　Q01 测试设计，B03/B06 后端和测试随实现首测。Q02 产品回归。对应 A19/A19-a/A27/A28。

**前置**　有可运行的接收、扫描、代际和结算候选，能读取已提交的空间账目并独立控制业务时钟。实际写入及回收分支依赖通过 TR01/TR02 的路径。

1. 将合成空间置于只够一份上传预留的剩余额度。用并发屏障同时请求两次预留，分别覆盖不同请求键的配额竞争、上传中断及重复提交完整内容。核对剩余额度、失败原因与下一步指引。安排同空间已归档项目参与初始占用，再用另一空间的独立账目做对照。
2. 固定业务时钟，令一张图片在第 14 分钟完整接收，延后扫描至第 20 分钟。第 15 分钟运行接收过期处理，并发申请足以填满剩余额度的新上传。观测原件实际字节结算及图片最多 2 MiB 衍生预算由接收预留转入 `PROCESSING`。对照 PDF 无预览预留。检查原件与预览均在各自额度内，附件进入 READY 后才可按权限签发下载。
3. 以存在待决外部写入的上传覆盖取消/失败。用 TR02 的终结证据和清理故障点，在旧代占满时领取新代，确认 `WAITING_CLEANUP`、阻塞告警与后续合法候补。证据齐备且清理成功后，在账目提交前中断回收，再重放。以发布和下载请求检查非 READY 对象始终不可用。

**观测**　`storage_used_bytes`、`storage_reserved_bytes`、`quota_bytes`、预留及处理代际、原件实际字节、接收过期时刻、任务和清理事务标识、可用额度提示、结算次数及鉴权结果。保存各屏障处的已提交账目和对象状态。

**判定**　通过要求每个已提交状态中占用与预留之和不超过配额，原件结算与衍生预算/任务绑定同事务，接收过期保留处理预算，失败清理前保账，成功后只释放一次，归档仍占额且其他空间不受影响。违反任一恒等关系、越权读取或额度重复释放判失败。只查最终余额或无法关联对象、预算和提交次序时为证据不足。

**停止与清理**　一旦超额或结算漂移，关停测试空间的新写入。按台账核对残留和预留，保全首次偏差快照；确认终结与清理后复核空间计量。

## TR04 · 决定与发布、撤销的并发顺序

**阶段与责任**　Q01 测试设计，B02/B04/B05 后端和测试随实现首测。Q02 产品回归。对应 A11/A12/A15。

**前置**　候选含项目更新、分享撤销和决定事务，可用独立 PostgreSQL 连接确定获锁及提交顺序。每个胜负分支从同一业务基线独立构造。

1. 准备有效客户会话、本轮 IN_REVIEW 版本、已有评论和可发布草稿。用独立连接及不同幂等键同时发出合法的确认与需要修改，分别控制二者抢先获锁。记录两条 API 响应、实际提交顺序和唯一约束结果。获胜请求返回 `201`。落败方在仍持有效授权、指向正确版本且请求其他字段合法时，返回 `409 ALREADY_DECIDED`，通过读接口取得既有决定和记录。
2. 分别令旧版决定或新版发布先提交。发布先提交时旧审阅轮撤回、旧分享和会话撤销，旧决定失败。若决定先提交，旧决定及固定记录保留。若新版成功发布，新版独立审阅且无继承决定；若 revision 冲突则按 API 刷新并显式处理，记录实际冲突。另用分享撤销与评论、分享撤销与决定两组竞态覆盖两个提交顺序。
3. 同时放置读请求验证界面显示的当前版、历史版记录和旧会话响应。决定后评论拒绝，决定快照与决定前已提交的评论相符；撤销先提交时无后继客户写入，撤销后不签发新下载链接。

**观测**　事务及锁顺序、当前版本指针、版本状态/revision、分享和会话撤销时刻、决定/记录行数及摘要、评论时间、成功审计、站内通知和通知待发事件关联、HTTP 状态和错误码。注入前保存相同业务状态的对照。

**判定**　通过要求每组预定提交顺序得到可解释的唯一结果，业务状态、决定、记录、审计和通知待发事件一致。出现两份决定、孤立记录、撤销后客户写入或新版继承旧决定判失败。若并发只发生在浏览器而未证实数据库竞争，或任一规定顺序未能触发，为证据不足。

**停止与清理**　发现越权或重复决定时停测试入口，保全相关行和事务轨迹，再撤销合成会话并回收合成记录。

## TR05 · 幂等竞争、事务崩溃与权限重验

**阶段与责任**　Q01 测试设计，相关后端和测试随实现首测。Q02 产品 API 回归。对应 A13/A32。

**前置**　候选包含真实数据库的幂等事务和身份校验，准备两个空间及对应角色，具备确认数据库提交、重启测试进程和丢弃返回响应的观测点。

1. 对项目创建和评论分别发同身份/同目标路由/同键/同请求的并发调用，固定首个事务持锁。第二请求应等待；另设一组超时返回 503，之后同键重试。改用同键不同内容预期 409；另用其他空间的相同键验证隔离。
2. 在写入业务和结果引用之后、提交之前中断应用进程。用独立连接核对幂等占位、业务、副作用均回滚，再用同键完成一次。再于成功提交后丢弃响应，同键重发项目/评论以及决定，对比原业务 ID 和决定的原记录及通知待发事件次数。
3. 在失效身份的独立分支移除成员、撤销分享或请求删除，再以原身份重放以核对访问控制。具备当前权限的同键同内容成功重放为 `200`，带本次 `request_id` 和原业务结果。发布重放的 `data` 含原 `version`、`share_id` 和 `secret_replay_available=false`。分享重发的重放含原 `share_id` 和 `secret_replay_available=false`。两者均不得重复生成授权或返回原始链接、令牌及签名。

**观测**　可信 actor_scope 和 route、键的匿名引用、请求摘要、锁等待和回滚/提交时刻、幂等结果引用、HTTP 状态、业务 ID、记录及待发事件、身份有效性及幂等记录数量。

**判定**　各自只有一份提交的业务对象及结果，崩溃前后分支符合原子性，冲突/等待超时按 API 返回，失效身份无缓存内容，判为通过。分裂提交、双写、缓存越权或重放密钥判失败。无法区分提交前后，或只观察 HTTP 而缺数据库证据时为证据不足。

## TR06 · 删除授权、代际、期限与失败补救

## TR07 · 带删除清单的隔离恢复

**阶段与责任**　O01 运维执行，测试复核；O02-PRE 纳入演练。对应 A17/A24。

**前置**　准备隔离恢复目标、数据库恢复点、对象独立备份、一致性清单及更新的删除清单。测试目标共有至少 10 个可抽检版本，并有独立验证入口权限与对象摘要的人员。

2. 用旧数据库备份及匹配的原件/预览恢复，先应用最新删除清单，再轮换或撤销恢复出来的旧会话和分享，完成后才开放隔离检验入口。另试删除清单缺失、过旧或匹配对象缺失的情形，核对入口继续关闭且一致点未被标记成功。

**判定**　通过要求清单和旧凭据处理先于开放，已删除内容不可再读，抽检与合成链路一致。整体 RPO 不超过 24 小时，按数据库和文件较差值计算。整体 RTO 不超过 4 小时，数据库独立 RPO 不超过 15 分钟。数据复活、漏文件、入口提前开放或超过目标判失败。缺实际恢复时间、完整点或抽检证据时为证据不足。
