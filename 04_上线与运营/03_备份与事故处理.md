# 备份与事故处理

负责人：运维；协作：技术、产品、运营。目标需要演练验证，不是已达成的服务承诺。

## 恢复目标与保存

整体业务恢复点目标RPO不超过24小时，恢复时间目标RTO不超过4小时。数据库单独目标RPO不超过15分钟，由托管服务PITR能力支持；文件备份按每日一致性清单执行，因此不能把数据库15分钟直接宣称为整个系统RPO。

数据库保留连续日志与每日备份；对象采用版本保护及每日独立备份/复制清单，放到生产应用不可删除的权限边界；配置与密钥恢复路径分别保管。每份备份自生成起最长保留35天；活动数据最迟请求后30天清理，因此残留备份最迟可能在请求后65天过期，恢复时必须先应用删除清单。云商可用功能、价格、版本保护和跨账号备份方式须在采购时验证。

备份内容包含数据库、原件、预览、文件摘要清单及删除清单。只备份数据库不能恢复文件；只有桶版本也不能替代独立备份。每日确认数据库时间点与文件清单可匹配，发现缺文件则最近完整恢复点不得标记成功。

## 恢复演练步骤

1. 选定目标业务时间点，建立隔离环境并禁止出站邮件。
2. 恢复数据库到不晚于该业务点的可用状态，恢复相应对象与版本。
3. 加载比备份更新的删除清单；先清除应删除数据，再允许任何测试访问。
4. 轮换或撤销恢复出来的会话和分享授权，避免旧凭据复活；保留历史决定。
5. 核对项目/版本/附件数量，抽检不少于10个版本及全部抽检附件摘要，检查权限和决定唯一性。
6. 用合成项目执行完整链路，测量总恢复时间和实际数据损失窗口。
7. 记录成功、失败、遗漏、修复责任人和下次演练日期。首次公开试点前完成，此后至少每月一次及重大迁移后执行。

如恢复到过去状态，已向客户确认成功但不在恢复点内的操作可能丢失。必须按审计、业务记录与用户沟通进行核对，不能静默重建或伪造决定。RPO的业务风险应在服务说明中真实表达。

## 故障处置

| 故障 | 首要动作 | 恢复检查 |
|---|---|---|
| 应用不可用 | 看部署变化和探活，必要时回滚应用 | 核心合成检查及错误率 |
| 数据库故障 | 停写，检查托管状态及备份 | 事务一致性、恢复点与缺失窗口 |
| 扫描任务积压 | 检查Worker、磁盘及病毒库 | 不放行未检查文件，验证队列消退 |
| 邮件服务故障 | 保留待发任务，显示中性重试提示 | 目标邮箱实际送达，过期码不投递 |
| 文件疑似泄露 | 撤销授权、必要时冻结空间或下载入口 | 访问范围、签发URL窗口、已下载边界 |
| 错误删除 | 隔离现场，找匹配备份和删除原因 | 恢复不得越过合法删除意愿 |
| 成本异常 | 查流量/任务来源，限制异常入口 | 恢复正常用量且核心流程不被误封 |

## 事故分工与沟通

技术负责人指挥定位，运维执行隔离与恢复，测试验证，运营负责用户通知和必要的外部报告核验。保存最少必要证据，避免把敏感数据扩散到群聊。对外说明已知影响、已采取措施、下一次更新时间，不猜测未查明原因。

高优先级事故在处置后两个工作日内复盘：发生和发现时间线、根因、影响、检测缺口、修复、预防任务、责任人及期限。复盘聚焦系统改进，不以删除错误日志掩盖问题。
